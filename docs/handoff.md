# 引き継ぎ文書 — 語灯 (gotou)

この文書は、企画フェーズ(2026-07-24〜25)から実装フェーズ(Claude Code)への引き継ぎである。
毎回守るルールは各 CLAUDE.md を参照。ここには経緯と現状と直近タスクを書く。

## プロジェクト概要

浄土宗大辞典(https://jodoshuzensho.jp/daijiten/ 、MediaWiki・約1万項目)をスマホで引ける
辞書アプリ。正式名は「語灯(ごとう) ― 浄土のことば辞典」、愛称はマスコットの「ごとうさん」。
主対象は檀家・信徒。開発者は浄土宗僧侶の一人開発(Python経験あり)。

## 現状(2026-08-01時点)

- `factory/src/` に既存のPythonスクリプト(記事・画像取得、.Dictionary出力)を受け入れ済み。
  `wikitext.py` に変換ロジックを共通化し、`build_sqlite.py` で `shared/schema.sql` 準拠の
  SQLite(FTS5・links・aliasesテーブル含む)を出力できる。`--source {cache,fixtures}` で
  実データ/ダミーfixtureを切り替え可能(既定値`cache`)。pytest 16件、全pass。
- `app/` はVite+React+TSで、検索モード(読みインクリメンタル・異体字対応・実SQLクエリ)と
  勤行モード(差定プリセット選択・編集・共有機能つき)を実装済み。辞書DBは
  `@sqlite.org/sqlite-wasm`経由で読む。項目本文はfactoryと同等の変換ロジック
  (TS移植版、後述)が生成したHTML(body_html)をそのまま表示し、内部リンクの
  クリックでアプリ内ジャンプする。記事切り替え時は本文エリア(`.detail`)の先頭が
  必ず画面内に入るようscrollIntoViewする(検索結果一覧が長い場合や、長文記事の
  末尾リンクから短い記事へ移動した場合でも迷わないように)。vitest 143件、全pass。
- **PWA化完了**: Web App Manifest + 手書きのService Worker(`app/public/sw.js`)で
  アプリシェルのオフライン起動・ホーム画面追加に対応。vite-plugin-pwa等は使わず素の
  Cache API/Service Worker APIで実装(app/CLAUDE.mdの「Web標準から外れる実装を避ける」
  方針に沿う)。アイコンは開発者の正式素材待ちの仮素材(提灯モチーフ)。新しいSWが
  待機中になったら「アプリの更新があります」バナーを表示し、ユーザーが「再読み込み」を
  押したときだけskipWaitingする定番パターンも実装済み(自動でセッションを切り替えない)。
- **辞書データ取得の経路を刷新(アプリが自分で浄土宗大辞典に直接アクセス)**:
  当初は「factory(Python)が事前にクロール・変換したSQLiteを、アプリが静的ファイルとして
  ダウンロードする」構成だったが、これだと変換済みの実データのコピーを自分たちの
  サーバー/リポジトリで保持・再配布することになり、無許諾での「公開・再配布」に当たる
  懸念があった。そこで`factory/src/fetch_articles.py`(取得)・`wikitext.py`(変換)・
  `build_sqlite.py`(SQLite構築)相当のロジックをTypeScriptに移植し
  (`app/src/lib/mediawikiFetch.ts`・`wikitextConvert.ts`・`buildDictionaryDb.ts`・
  オーケストレーションの`dictionaryAcquisition.ts`)、**ユーザー自身のスマホが
  浄土宗大辞典のMediaWiki API(`origin=*`パラメータでCORS許可されていることを実機で
  確認済み)に直接アクセスして変換する**構成に変更した。実データは各ユーザーの
  ブラウザのCache Storageにのみ保存され、リポジトリ・自前サーバーには一切残らない。
  ダウンロードは「PWAインストール済み+ダウンロードボタンの明示的タップ」を条件に
  発生し(`app/src/lib/pwaDisplayMode.ts`の`isStandalonePwa()`で判定)、これは
  **公開GitHub Pagesサイトの実際の挙動**として反映済み(2026-08-01、開発者の明示的な
  承認による)。旧来の静的ファイルダウンロード経路(`getDictionaryBytes`)は
  SearchMode.tsxから完全に置き換えられ、dev/test/CIで使うダミーデータ生成
  (`build-dummy-db.mjs`)は開発・自動テスト専用として引き続き残っている。
  実機9,197件全件での取得・変換・検索・内部リンク遷移・2回目以降のキャッシュ
  自動読込までブラウザで確認済み。
- **勤行テキストデータ**: 日常勤行式(香偈〜送仏偈、全18項目)に加え、法要
  (施餓鬼会・棚経)関連の偈文・陀羅尼・回向文13件(破地獄偈・敬禮六位・變食陀羅尼・
  甘露水陀羅尼・乳海陀羅尼・阿彌陀如來根本陀羅尼・餓鬼回向文・回向文3種・
  聞名得益偈・一切精靈偈・誦経(仏説観無量寿経 第九真身観文))を`shared/gongyo/units/`に
  収録。差定は日常勤行式2種(四奉請・三奉請)に加えて棚経2種
  (`tanagyo-shinbo`=新亡回向、`tanagyo-senzo-daidai`=先祖代々)を用意。
  読み(ruby)は開発者(僧侶)による直接の点検・修正、または開発者が「参照可」と
  明示した外部サイトとの照合を経て確定させている。
- **勤行モードの表示モデルを刷新**: 従来の「body 1行=1ページ」から、通常のunitは
  body全体を1画面にグループ表示(行数に応じて文字サイズ自動縮小)、誦経・一枚起請文・
  長い陀羅尼等(`paginated: true`)は複数行ずつバッチでページ送りする方式に変更。
  バッチ行数は1句あたりの文字数から自動決定(`paginatedBatchSize`、短い句ほど
  多く一度に見せる)、次ページ冒頭に前ページ最終行を薄くエコー表示して続きを
  分かりやすくしている。常時ラベル(差定名・偈文名)、勤行開始時の導入画面
  (差定名を最初に表示)、本文の左揃え+左マージン(経本に慣れた読み手向け)も追加。
  詳細は`docs/saijo-spec.md`参照。
- **縦書き(経本)表示に対応、かつ既定を縦書きに変更**: 経本は基本的に縦書きで、
  それに見慣れた利用者の方が多いため。ヘッダーのトグルでいつでも横書きに切り替えられ、
  選択はlocalStorage(`gotou:gongyo-orientation`)に保存される。
  CSSは`writing-mode: vertical-rl`を`.gongyo-lines`にだけ掛ける方式で、既存の
  `flex-direction: column`がそのまま右→左の行送りになり、ルビも自動的に各行の右側へ回る
  (行の並べ替えロジックもマークアップ変更も不要だった)。カウンターは縦書き文脈に
  置くと数字が横倒しになるため、`.gongyo-body`側に残して横書きのまま表示している。
  縦書きは横書きと制約が逆転する(行数=画面の横幅、1行の長さ=画面の高さ)。
  横書きのように字数から段階(tier)を決め打ちすると、375px幅に合わせた閾値が
  360px幅の端末でははみ出す、という具合に端末ごとに破綻したため、縦書きでは
  列数と1列に必要な字数だけをCSSカスタムプロパティで渡し、字送りはCSSの
  `min()`が画面の実寸から決める方式にした(320/360/375px幅で全unitの
  収まりを実測確認済み)。1タップで進む行数だけは内容の判断なのでTS側
  (`verticalPaginatedBatchSize`)に残している。
  あわせて縦書きでは表示時にbodyを組み替える(`verticalBody`): 短い句(8字以下)
  ばかりのunitは2句ずつ1列にまとめ(四誓偈・摂益文で列の下半分が空くのを解消)、
  長すぎる句(60字超)は句読点で区切って複数ページに分ける(一枚起請文の114字を
  1ページに載せると字が19pxまで縮んでいたのを40px前後まで拡大)。
  向きを切り替えるとページ分割が変わるが、読誦中の偈文の先頭に留まるようにしてある。
- **差定プリセット選択UI・編集操作・共有機能完了**: `docs/saijo-spec.md`が規定する
  「複製→編集」の動線を実装。プリセット選択画面、複製した差定の並べ替え・オンオフ・
  回数指定編集、localStorageへの永続化(spec原案のIndexedDBから変更)に対応。
  さらにQRコード/URL/JSONでの差定共有(`qrcode.react`使用、受信側はURL開くだけで
  取り込み確認画面が出る)も実装済み。
- **GitHub Pages公開完了**: リポジトリをパブリック化し、
  https://letticia.github.io/gotou/ で公開中。`main`へのpush毎にActions経由で自動デプロイ。
  ダミーfixtureデータとPD勤行テキストのみを公開しており、実データ・許諾が絡む記述は
  Git履歴からも削除済み(`docs/plan-2026-07.html`は完全削除)。プロトタイプ注記バナー・
  `noindex`メタタグで非公式・開発中であることを明示している。
- GitHub Actions(`.github/workflows/ci.yml`)でfactory pytest・app vitest/buildの検証と
  Pagesデプロイをpush時に自動実行するようにした。
- 辞書データの利用許諾は依然として未取得。CLAUDE.mdの掟(大辞典由来データを
  コミット・公開しない)は変わらず守っており、上記のliveモードでも実データを

## 決定事項サマリ

- **技術**: TypeScript/React のPWA。辞書DBは **`@sqlite.org/sqlite-wasm`**
  (sql.jsは標準ビルドがFTS5を含まずshared/schema.sqlのentries_ftsが作れないため不採用)。
  `sqlite3.capi.sqlite3_js_db_export`でDBをUint8Arrayへシリアライズできるため、
  ブラウザ内で構築したSQLiteもCache APIにそのまま保存できる。GitHub Pages + Actionsで
  配信中(base pathは`VITE_BASE_PATH`環境変数で切替、既定は`/`のまま)。将来Capacitorでの
  ストア展開も見据え、Service Worker等は素のWeb標準APIで実装している。
- **辞書データの取得元**: factoryが事前変換したSQLiteの配信ではなく、アプリ自身が
  浄土宗大辞典のMediaWiki APIに直接アクセスして取得・変換する(上記「現状」参照)。
  factory(Python)は`.Dictionary`(macOS)出力やdev/test/CIのダミーデータ生成としては
  引き続き使う。factoryとappの変換ロジック(wikitext.py / wikitextConvert.ts)は
  独立した並行実装で、出力が一致するようテストで突き合わせている。
- **検索**: 読みのインクリメンタル・前方一致が主役。異体字は shared/variants.json で吸収。
  実装済み。音声入力(kuromoji.jsで読みに戻す)は標準辞書では見送り、カメラOCR
  (収録語スキャン)も見送り(いずれも下記「作業時の注意」参照)。
- **勤行モード**: 差定をプレイリストとして扱う(docs/saijo-spec.md)。日常勤行式・
  法要(施餓鬼会・棚経)一式、プリセット選択/編集/共有まで実装済み。表示は
  グループ表示(既定)とpaginatedバッチ送り(長文unit)の2方式。縦書き(経本)表示は
  実装済みで既定。回転ロック、テンポ式オートスクロール(v1.5)は未着手。
- **データ取得〜表示の一気通貫**: wikitext→HTML変換はfactory(Python)とapp(TS)の
  独立した並行実装だが、内部リンクのhref形式など出力仕様は完全に一致させており、
  appは変換結果のHTMLをそのまま表示する(表示側での簡易再パースはしていない)。
- **計測**: Plausible/Umami 系、未着手。
- **公開範囲**: リポジトリはパブリック。ただし許諾交渉に関わる記述はコミット・履歴の
  両方から意図的に除外している(下記「連絡・確認の掟」参照)。
- **モデル運用**: 実装はSonnet。設計はプランモードで計画してから着手(本セッションで一貫)。

## 作業時の注意(教訓)

- `factory/src/build_sqlite.py` などfactoryのスクリプトは、引数を省略すると
  `factory/cache/`(実データ)をデフォルトで読む。ダミーfixtureで作業する際は
  `--source fixtures` を必ず明示し、実行後は `git status --ignored` で
  `factory/output/`・`factory/cache/`・`app/public/` に実データ由来のファイルが
  紛れ込んでいないか確認すること。
- 勤行テキストの読み(ruby)は、参考にした公式サイト・PDF等をそのまま複製せず自前で
  付与する方針(docs/saijo-spec.md)。ただし開発者から「参照用途として使ってよい」と
  明示された場合はその本文・読みと直接照合してよい。読みの正誤は開発者(僧侶)にしか
  判断できないため、確信が持てない箇所は都度確認すること。
- 勤行モードの表示調整(文字サイズ・行数)は、unitごとの本文を手で書き換えるのではなく、
  `app/src/lib/gongyo.ts`側の汎用ロジック(`lineSizeTier`/`paginatedSizeTier`/
  `paginatedBatchSize`)で解決する方が、将来unitが増えたときも自動的に適切な
  表示になり保守しやすい。
- 「実データを公開してよいか」の判断は、静的ファイルとして自分たちが配信するのか、
  ユーザー端末が直接取得するのかで結論が変わりうる。後者は「個々のユーザーが
  ブラウザでサイトを閲覧するのと同じ」という整理が成り立つため、無許諾でも
  開発者の判断で進められる場合がある。ただしこれは開発者(僧侶、当事者)自身の
  判断であり、勝手に推測して進めてはならない。
  実際にこのセッションでも、一度は「保留したい」との判断が出た後、開発者から
  「PWAインストール+ダウンロードボタンの明示的タップ」という利用者の意思表示を
  条件とする再整理が示され、それを受けて実装した経緯がある。
- CORSが使えるかは`curl`では分からない(CORSはブラウザが強制するものであり、
  サーバーへの直接リクエストは常に成功する)。実機のブラウザから`fetch()`を
  実行して確認する必要がある(`origin=*`パラメータの有無、レスポンスヘッダの
  可視性で判断できる)。
- CI実行結果を`gh run list --commit <SHA>`で確認する際、短縮SHA(7桁)は
  マッチしないことがある。`git rev-parse HEAD`で得たフルSHAを使うか、
  `--commit`オプション自体を使わず`--limit`で直接絞り込むこと。
- 記事間遷移時のスクロール位置は「ページ先頭」ではなく「本文エリア
  (`.detail`要素)」をscrollIntoViewするのが正しい。検索結果一覧は
  クエリが空にならない限り本文の上に表示され続けるため、一覧が長いと
  ページ先頭に戻るだけでは本文が見えないままになる。
- 縦書き(`writing-mode: vertical-rl`)は、既存の`flex-direction: column`が
  そのまま右→左の行送りになり、独立した`<p>`のルビも自動的に行の右側へ回る。
  つまり**マークアップも並べ替えロジックも変更不要**で、CSSだけで経本の体裁になる。
  ただし縦書き文脈に入れた数字は横倒しになるため、カウンター等は縦書きの
  外側(`.gongyo-body`側)に置いておくこと。
- `100vh`から固定値を引いて高さを決めると、プロトタイプ注記バナーのように
  画面幅で行数が変わる要素があるとはみ出す。**シェルを縦flexにして残り領域を
  `flex: 1`で占める**方が確実(`.shell-gongyo`/`.gongyo`)。この方式に変えるときは、
  `margin: 0 auto`を持つ子要素(`.mode-tabs`)が交差軸のstretchを失って
  内容幅まで縮む点に注意する(幅を明示して回避する)。
- 読誦位置を「どのunitか」で覚えると、同じunitが差定に複数回現れる場合
  (日常勤行式の十念は4回)に最初の1回へ戻ってしまう。`GongyoPage.itemIndex`
  (preset.items内の位置)で覚えること。
- 文字サイズを「字数から段階を決め打ち」する方式は、特定の画面幅に合わせた
  閾値が他の幅で破綻する。縦書きではCSSの`min()`/`max()`と
  カスタムプロパティ(列数・必要字数)で画面の実寸から決めるようにした。
  横書き側は既存の段階方式のままだが、同種の問題を抱えている点は留意。
- 縦書きの「1列に何字入るか」の見積り(`VERTICAL_CHARS_PER_COLUMN`)を小さくしすぎると、
  実際には折り返さない句まで複数列と数えてしまい、1列の幅を狭く見積もって字が
  不必要に小さくなる(15字にしたとき320px幅で四奉請が11.7pxまで縮んだ)。
  実測(320〜375px幅で1列16〜19字)に合わせて20字としている。
- 縦書きで長い行を折り返させるには`.gongyo-lines`に`align-items: stretch`が要る。
  `flex-start`だと行の高さが内容なりになり、一枚起請文の114字が折り返さず
  画面外へ突き抜ける。またサイズの下限(`max()`)は高さの制約にだけ掛けること。
  幅の制約に下限を掛けると、狭い端末で列がはみ出す。
- `.gongyo-body`が`align-items: flex-start`(内容に合わせて幅を決める)の状態で、
  ネストしたflexコンテナに極端に長い1行(分割しない一枚起請文の114字等)が
  混じると、折り返さずコンテナ幅を超えて広がることがある(横書きモードで発生)。
  `.gongyo-lines`/`.gongyo-line-group`に`max-width: 100%`を明示して解決した。
  この種の「shrink-to-fitの計算がおかしい」系の不具合は、ブラウザの表示スケールが
  ずれて見える別の問題(下記)と紛らわしいので、`getBoundingClientRect()`で
  本文幅とコンテナ幅を**比率で**比較して切り分けること(絶対値は環境依存でずれても、
  本文がコンテナより広いという相対関係は変わらない)。
- **縦書きの字送りが見込む「本文以外に取られる高さ」は、クロムを変えたら必ず
  実測し直すこと**(`--gongyo-chrome`、旧`16rem`)。この定数が実態からずれても
  過大なら字が小さくなるだけで気付きにくいが、過小だと1列に収まらず左の列へ
  あふれて列数が狂う。2026-08-09の実測値は、カウンター無し10.2rem・
  偈文名ラベルが2行11.86rem・カウンター有り14.14remで、余裕を見て
  12rem/14.5rem(`.gongyo-has-counter`)としている。**カウンターの有無で
  4rem近く変わる**ため、一定値ではなくクラスで出し分けている。
- ブラウザ操作ツールで勤行を全ページ走査すると、ペインが隠れている間は
  タイマーが強く間引かれて`javascript_tool`が30秒でタイムアウトする。
  十念のようなカウンター付きunitは1ページに10タップ必要で余計に遅い。
  特定unitだけを検証したいときは、`localStorage`の`gotou:user-presets`と
  `gotou:last-preset-id`に検証用の差定(そのunit1件だけ)を直接書き込んでから
  リロードするのが速い(検証後は消すこと)。
- **カメラOCRはTesseract.jsの標準日本語モデルでは実用に耐えないと判明(2026-08-09検証、
  実装はせず見送り)**: Google Fonts配布のNoto Serif JPで合成レンダリングした語10件
  (現代表記・異体字/旧字体混在)をhorizontal(`jpn`, PSM7)・vertical(`jpn_vert`, PSM5)
  両方でOCRしたところ、完全一致3/10・文字誤り率30〜35%だった。しかも間違えるのは
  決まって`彌`・`佛`・`壽`・`經`・`會`など**この辞書が専門にする異体字・旧字体**で、
  現代表記(一枚起請文・摂益文等)は素で正解する。合成のクリーン画像でこの精度なので、
  実際にスマホで書籍を撮影した写真ではさらに悪化すると見るべき。代替として
  部首・画数引きや手書き入力を検討する方向に転換した(実データも大辞典由来データも
  一切使わず、自前でレンダリングした一般的な仏教語のみで検証している)。
- **音声入力用の読み復元(kuromoji.js標準辞書)は仏教語に対して実用に耐えないと判明
  (2026-08-16検証、実装はせず見送り)**: `shared/gongyo/units/`(パブリックドメイン・
  開発者検証済みのふりがな付き勤行テキスト)から抽出した246件のtext/ruby対で、
  kuromoji.js(標準辞書=mecab-ipadic)によるtokenize→読み(カタカナ)抽出→ひらがな変換の
  結果を正解のふりがなと突き合わせたところ、完全一致率5.7%(14/246)・平均文字誤り率
  50.6%だった。unit名(見出し語相当、30件)に絞っても完全一致率16.7%・誤り率50.8%で
  改善しない。OCRのときと違い、誤りは異体字・旧字体などレアな文字に限らず**ごく普通の
  漢字を含む複合語全体**で起きる: 標準辞書は現代の口語・時事文向けの読み(訓読み・
  一般的な音読み)を採用するため、仏教語特有の音読み(「回向文」→誤"えこうぶん"/
  正"えこうもん"、「念仏一会」→誤"いちかい"/正"いちえ"、「開経偈」→誤"ひらきけいげ"/
  正"かいきょうげ")や、辞書自体に無い専門語・人名(「阿難(あーなん)」→誤"おもねがた"、
  「須弥山(しゅーみーせん)」→誤"須ややま"、須の字が未知語として素通り)を軒並み外す。
  これは訓練データを増やせば直る類の誤差ではなく、汎用辞書(mecab-ipadic)と仏教語彙の
  構造的な不一致(読みの体系そのものが違う)であり、カメラOCRの結論よりもむしろ根が
  深い。代替案として「大辞典側の見出し語+読みのペア(自前データ、外部提供不要)から
  kuromoji用のユーザー辞書を構築する」道も検討したが、単語境界の扱いや複合語への
  対応を含む別プロジェクト規模になる見込みのため、開発者の判断で工数的に見送り
  (2026-08-16)。音声入力機能自体、当面着手しない。検証スクリプト自体はリポジトリに
  コミットしていない(OCRスパイクと同じ扱い)。
- **iPhoneのSafariで、誦経等paginated unitのページ送り時に本文の一部(画面下側)が
  前ページの残像のまま更新されない不具合が報告された(2026-08-10)**。原因は
  `GongyoMode.tsx`の`.gongyo-lines`直下の行要素がpage.lines内の位置(0,1,2...)を
  keyにしていたため、ページごとの行数が同じ場合Reactが既存DOMノードを再利用して
  テキストだけ差し替える形になっていたこと。縦書き(`writing-mode: vertical-rl`)+
  ネストしたflex(`.gongyo-line-group`・`height: max-content`等)という構成で、
  iPhone Safariはこの「同一要素内でのテキスト差し替え」を正しく再描画しないことが
  ある。`.gongyo-lines`に`key={nav.pageIndex}`を付けてページごとに要素ごと
  作り直すよう変更して解決(この種のブラウザ固有の再描画バグは、Reactのkeyで
  要素を強制的に作り直すのが最も確実な回避策になりやすい)。
  この開発機にはXcodeがフルインストールされておらずiOS Simulatorが使えなかったため
  当初は実機未検証だったが、開発者が実機Safariで確認済み(2026-08-16、解決確認)。
- Service Workerの事前キャッシュ(`PRECACHE_URLS`)にHTMLシェル・manifest・アイコンしか
  入っていないと、`vite build`が生成するハッシュ付きJS/CSS・SQLite wasm/ワーカースクリプトは
  「一度オンラインで実際にリクエストされた」ときに`cacheFirstRuntimeCache`が後追いで
  キャッシュするだけになる。SWが新しく有効化された直後、まだ何もランタイムキャッシュ
  されていないタイミングでオフラインになると、アプリ本体のJSすら読み込めず
  起動時のスプラッシュ(アイコン)から進まなくなる(Android/機内モードで実際に発生・
  2026-08-09確認)。修正は`app/scripts/generate-sw-precache.mjs`という`postbuild`スクリプトで、
  `vite build`後に`dist/assets/`の実ファイル名を`dist/sw.js`の`PRECACHE_URLS`へ機械的に
  反映し、あわせて`SHELL_CACHE`名もアセット一覧のハッシュで自動バージョニングする
  (ビルドごとに値が変わり、既存のactivate時クリーンアップが前回ビルドの古いキャッシュを
  自動で捨てるようになる)。フォント(`app/public/fonts/`、3書体×740ファイル)は意図的に
  対象外のまま: 欠けてもシステムフォントへ自然にフォールバックするだけで起動失敗には
  ならないため、既存の「使った分だけ遅延キャッシュ」で問題ない。
- 横書きの`paginatedBatchSize`は句の長さに関わらず一律で「3句にまとめる」ため、
  一枚起請文のように句ごとの文字数が大きく異なる(14字〜114字)unitでは、
  3句分の折り返した本文が画面の高さを超えることがある。60字を超える句を持つ
  unitは1句ずつに減らすことで解決(縦書き側は元々`verticalPaginatedBatchSize`で
  同種の調整をしていたが、横書き側は未対応だった)。
- ブラウザ操作ツール(`mcp__Claude_Browser__*`)は、`navigate`に`force: true`を
  付けたり複数回`preview_start`/`preview_stop`を繰り返したりすると、
  `resize_window`で設定したはずのモバイル幅(375x812)が反映されず
  `window.innerWidth`が実際のペイン幅(705等)を返すことがある。測定前に
  必ず`window.innerWidth`を確認し、ずれていたら`resize_window`をやり直すか
  `force`無しで`navigate`し直すこと。
- Reactの状態更新は、同一の`javascript_exec`スクリプト内で
  `element.click()`した直後に`document.querySelector(...)`しても
  まだ反映されていないことがある(React 18のイベントバッチング)。
  クリックと検証は**別々の**`javascript_exec`呼び出しに分けること。
- Google FontsのCJK書体(Noto Serif JP等)はUnicode範囲ごとに数十〜百数十個の
  woff2に分割配信される。自前ホスティングする際も`unicode-range`をそのまま
  保持すれば、ブラウザは実際に使う文字のサブセットだけを取得する
  (=全ファイルを同時に読み込むわけではない)ため、全サブセットをまとめて
  ダウンロード・コミットしても実運用の通信量は増えない。逆に「よく使う文字だけ
  自分で見繕って絞る」方が、辞書本文にどんな文字が出てくるか事前に分からない
  以上リスクが高い(Googleの分割をそのまま複製する方が安全)。
